## 1. Запуск контейнера

Для демонстрації використаємо вбудований Python HTTP-сервер.

Команда запуску:

```bash
docker run -d \
  --name python-web \
  -p 8080:8080 \
  python:3.12-slim \
  python -m http.server 8080
```

Перевірка:

```bash
docker ps
```

Приклад результату:

```text
CONTAINER ID   IMAGE              COMMAND                  STATUS
a1b2c3d4e5f6   python:3.12-slim   "python -m http.ser…"   Up 10 seconds
```

---

## 2. Аналіз процесу (PID 1)

Виконаємо команду всередині контейнера:

```bash
docker exec python-web ps -ef
```

Результат:

```text
UID          PID    PPID  C STIME TTY          TIME CMD
root           1       0  0 12:00 ?        00:00:00 python -m http.server 8080
root          12       1  0 12:01 ?        00:00:00 ps -ef
```

### Чому саме цей процес має PID 1?

У контейнері немає повноцінної операційної системи із системою ініціалізації (systemd або init).

Процес, вказаний у команді запуску контейнера:

```bash
python -m http.server 8080
```

стає головним процесом контейнера та отримує PID 1.

Docker вважає контейнер активним доти, доки працює процес PID 1. Якщо цей процес завершується — контейнер також завершується.

---

## 3. Завершення контейнера

Зупинка контейнера:

```bash
docker stop python-web
```

### Який сигнал отримує процес?

Під час виконання `docker stop` Docker надсилає процесу PID 1 сигнал:

```text
SIGTERM
```

Це коректний запит на завершення роботи.

Якщо процес завершується самостійно після отримання SIGTERM, контейнер одразу зупиняється.

### Що відбувається, якщо процес ігнорує сигнал?

Docker очікує завершення процесу протягом стандартного таймауту (10 секунд).

Якщо процес не завершується:

```text
SIGTERM -> очікування -> SIGKILL
```

Docker надсилає сигнал:

```text
SIGKILL
```

Після отримання SIGKILL процес примусово завершується ядром Linux, і контейнер зупиняється.

---

## 4. Перегляд логів

Отримання логів контейнера:

```bash
docker logs python-web
```

Приклад:

```text
172.17.0.1 - - [15/Jun/2026 12:05:10] "GET / HTTP/1.1" 200 -
172.17.0.1 - - [15/Jun/2026 12:05:11] "GET /favicon.ico HTTP/1.1" 404 -
```

### Звідки беруться логи?

Docker автоматично збирає:

* stdout (стандартний вивід);
* stderr (вивід помилок)

головного процесу контейнера (PID 1).

У нашому випадку Python HTTP-сервер записує інформацію про HTTP-запити у stdout, а Docker зберігає ці записи через драйвер логування (за замовчуванням `json-file`).

Саме тому команда:

```bash
docker logs python-web
```

відображає повідомлення сервера без додаткової конфігурації.

---

## Висновок

Життєвий цикл контейнера визначається процесом PID 1.

У цьому прикладі процесом PID 1 є:

```text
python -m http.server 8080
```

Контейнер існує доти, доки працює цей процес.

Після виконання:

```bash
docker stop python-web
```

Docker надсилає процесу сигнал SIGTERM. Якщо процес коректно завершується, контейнер зупиняється. Якщо процес ігнорує SIGTERM, Docker примусово завершує його сигналом SIGKILL.

Таким чином, контейнер не є окремою віртуальною машиною — його життєвий цикл повністю залежить від головного процесу всередині контейнера.
